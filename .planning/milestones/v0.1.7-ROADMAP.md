# Milestone v0.1.7: Stability & Preact Migration

**Status:** ✅ SHIPPED 2026-03-06
**Phases:** 1-4
**Total Plans:** 20

## Overview

This milestone hardened the extension host, raised test confidence, and migrated the active webview runtime to Preact while preserving the existing ACP contract. The shipped result is a more diagnosable host stack, smaller core files, stronger regression coverage, and a component-based webview that no longer depends on the old imperative rendering path.

## Phases

### Phase 1: Error Context

**Goal:** Add structured diagnostic context to CLI discovery, pipeline validation, connection failures, and process startup.
**Depends on:** None
**Plans:** 3 plans

Plans:

- [x] 01-01: Structured discovery diagnostics, startup context formatting, and requirement-focused unit test coverage
- [x] 01-02: Ordered validation stage checks, stable stage codes in errors, and focused tests for failure ordering and run suppression
- [x] 01-03: Stage-boundary error wrapping in SessionCoordinator and requirement-level tests for all tags and fallback paths

**Details:**
- CLI discovery failures now report normalized reason codes and attempted lookup sources.
- Preflight validation fails in a deterministic order with stable tags (`INVALID_FILES`, `INVALID_CONTEXT`, `INVALID_MODEL`).
- ACP lifecycle failures are tagged by layer (`TRANSPORT_ERROR`, `AUTH_ERROR`, `PROTOCOL_ERROR`) with compatible recovery semantics.

### Phase 2: File Size Compliance

**Goal:** Split the oversized host files below the 500-line convention without breaking public facades.
**Depends on:** Phase 1
**Plans:** 4 plans

Plans:

- [x] 02-01: New `acpRunRecovery.ts`, reduced `acpRunExecutor.ts`, and updated tests proving no regression
- [x] 02-02: New `sessionRecoveryHandler.ts`, reduced `sessionCoordinator.ts`, and regression tests for lifecycle parity
- [x] 02-03: New handler modules under `src/webview/`, reduced `webviewHandler.ts`, and focused parity tests
- [x] 02-04: New `processStartupProbe.ts`, reduced `processManager.ts`, updated startup tests, full-unit and line-count phase verification

**Details:**
- Recovery, routing, and startup probing logic moved into focused helpers while facade APIs stayed stable.
- All four targeted host files ended below 500 lines.
- The phase closed with full unit-suite verification and line-count guardrails.

### Phase 3: Test Coverage

**Details:**

- Phase verification passed on 2026-03-04, and the current repo still reflects that shipped state.

## Milestone Summary

**Key Accomplishments:**

- Structured host-side diagnostics now make discovery, validation, startup, and ACP failures actionable.
- Oversized host files were split into focused modules without breaking public integration boundaries.
- Coverage gates now protect the highest-risk infrastructure modules and overall suite health.
- The active webview runtime was migrated to Preact with component-based chat, composer, panels, and message rendering.
- Current verification passed with `npm run compile` and `npm run test:unit` (`337 passing`, `4 pending`) on 2026-03-06.

**Key Decisions:**

- Preserve the ACP contract and host-side facades while refactoring internals.
- Treat the Preact rewrite as a full runtime replacement instead of incremental legacy DOM patching.
- Enforce size and coverage outcomes with automated guardrails where practical.

**Issues Resolved:**

- Opaque discovery and startup failures without enough context to debug quickly.
- Four host-side files growing past the project’s size convention.
- Weak regression coverage in critical infrastructure modules.
- Imperative webview rendering architecture that had become difficult to maintain.

**Issues Deferred:**

- `PERF-02` message virtualization was not shipped in this milestone and remains a next-milestone candidate if profiling shows need.
- Some historical Phase 4 planning bookkeeping remained partial, so milestone closeout relies on both checked-in summaries and the passing verification artifact.

**Technical Debt Incurred:**

- Planning docs had drifted to the wrong milestone version (`v0.2.0`) and were corrected during closeout to match the shipped `v0.1.7` release metadata.
- The requirements backlog needs a fresh post-archive definition rather than continued reuse of this milestone’s requirement list.
